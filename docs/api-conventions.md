# כללי API

## עקרונות כלליים
- REST, עם גרסה בנתיב: `/api/v1/...`
- כל התשובות והבקשות ב-JSON; תיעוד מלא ב-OpenAPI, מתעדכן עם כל endpoint חדש.
- אימות: JWT ב-`Authorization: Bearer <token>`; Refresh token נפרד לחידוש.
- **כל בדיקת הרשאה מתבצעת בשרת** — Middleware/Guard שבודק תפקיד + סניף + בעלות על הרשומה,
  על כל endpoint, גם אם ה-Frontend כבר מסתיר את הכפתור המתאים.

## מניעת דריסת נתונים (Optimistic Locking)
ישויות רגישות (Vehicle, Lead, Deal, Quote) כוללות שדה `version`. עדכון שולח את ה-`version`
שנקרא; אם הוא לא תואם למה שבמסד הנתונים — התשובה `409 Conflict` עם הודעה ידידותית
("מישהו אחר עדכן את הרשומה הזו בינתיים, יש לרענן ולנסות שוב"), לא שגיאה טכנית.

## Idempotency
כל endpoint שיוצר עסקה, תשלום או מסמך מקבל כותרת `Idempotency-Key`. בקשה חוזרת עם אותו
מפתח מחזירה את התוצאה המקורית ולא יוצרת כפילות — קריטי למניעת "עסקה כפולה" בניתוק רשת.

## מחיקה
`DELETE` לא מוחק שורה — הוא מסמן `deleted_at` (מחיקה לוגית). מחיקה סופית אינה חשופה ב-API
הרגיל של MVP.

## יומן ביקורת (Audit Log)
כל endpoint שמבצע יצירה/עריכה/מחיקה/אישור על ישות רגישה (רכב, לקוח, עסקה, תשלום, הרשאות)
כותב אוטומטית רשומת `AuditLog` (מי, מה, מתי, ערך לפני/אחרי) — דרך Interceptor משותף, לא בכל
endpoint בנפרד, כדי שאי אפשר יהיה "לשכוח" לתעד.

## פורמט שגיאות
- למשתמש: הודעה בעברית פשוטה, בלי קוד שגיאה טכני ובלי Stack Trace (ראו `design-system.md`).
- ללוג הפנימי: קוד שגיאה מובנה, request id, ופרטים טכניים מלאים (לצורך דיבוג בלבד — אף פעם
  לא כולל סיסמה, טוקן או פרטי תשלום).

## Rate limiting ו-Webhooks (שלב 2 ואילך)
כשיתווספו אינטגרציות חיצוניות: Webhooks ייחתמו (HMAC), עם הגבלת קצב קריאות (Rate limiting)
ומפתחות API מוגבלי היקף. לא רלוונטי ל-MVP אך התשתית (Queue) תוכן מראש כדי לא לדרוש שינוי
ארכיטקטוני מאוחר יותר.
