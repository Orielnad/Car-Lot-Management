# ארכיטקטורה — מערכת ניהול מגרש רכבים

## סטטוס
שלב 0 (תכנון). מסמך זה הוא מקור האמת לארכיטקטורה, ומתעדכן כשמתקבלות החלטות נוספות
בתהליך ה-Discovery (סעיף 25 במסמך האפיון). אין לבנות תכונה שסותרת אותו בלי לעדכן אותו קודם.

## עקרונות מנחים (מתוך מסמך האפיון, סעיפים 18 ו-39.3)
- Backend עם API מתועד (OpenAPI); כל פעולה רגישה נבדקת בצד השרת — הסתרת כפתור בממשק אינה הרשאה.
- מסד נתונים רלציוני עם עסקאות (Transactions) ונעילות ברמת שורה, למניעת מכירת רכב כפול ועדכונים סותרים.
- מחיקה לוגית בלבד (`deleted_at`); היסטוריה עסקית לא נמחקת; שינויים רגישים מתועדים ביומן ביקורת.
- הפרדת סביבות Dev / Test / Prod; Migrations מתועדים והפיכים (עם סקריפט Rollback).
- תמיכה מלאה ב-RTL ובעברית פשוטה בממשק (ראו `design-system.md`).
- אינטגרציות חיצוניות (יד2, WhatsApp, סליקה, הנה"ח וכו') ממומשות מאחורי מתאם (Adapter) ייעודי, כך שאפשר להחליף ספק בלי לשנות את הליבה.

## מחסנית טכנולוגית
| שכבה | טכנולוגיה | למה |
|---|---|---|
| Frontend | React + TypeScript | תמיכה טובה ב-RTL, קהילה גדולה, מתאים לטבלאות מסוג Excel ולטפסים מודרכים |
| Backend | Node.js + TypeScript (NestJS) | מבנה מודולרי שמתאים לבניה הדרגתית לפי המודולים במסמך האפיון; תמיכה מובנית ב-OpenAPI |
| מסד נתונים | PostgreSQL | רלציוני, תומך בעסקאות ונעילות כנדרש בכלל העסקי "לא ניתן למכור אותו רכב פעמיים" |
| ORM / Migrations | Prisma | Migrations מתועדים, קריאים והפיכים |
| תורים (Queue) | Redis + BullMQ | הודעות, אוטומציות, הפקת מסמכים — נדרש משלב 2 ואילך, אך התשתית תוכן מוקדם |
| אחסון קבצים | אחסון תואם S3, מוצפן | קישורים זמניים להורדה, הגבלת סוג/גודל קובץ, ללא גישה ישירה |
| אימות | JWT + RBAC בצד שרת | MFA (TOTP) יתווסף כאופציה בהמשך |
| אירוח | ייקבע בפועל לפי תקציב (למשל Railway/Render להתחלה) | לא חוסם את הפיתוח; ניתן לשנות ללא שינוי בקוד האפליקציה |

## היקף (Scope) לשלב זה
מגרש רכבים יחיד, עם אפשרות למספר סניפים תחת אותו עסק (כנדרש כבר בסעיף 2 של מסמך האפיון).
המודל נבנה כך שלא יחסום הרחבה עתידית ל-Multi-tenant אמיתי (מספר עסקים נפרדים, שלב 4 בלבד),
אך שלב זה לא ייבנה כעת.

## מבנה מודולים (Epics) ל-MVP
1. משתמשים, הרשאות וסניפים (Auth / RBAC / Organization / Branch)
2. מלאי רכבים (Vehicle, סטטוסים, היסטוריה, עלויות בסיסיות)
3. CRM: לקוחות ולידים
4. משימות ויומן
5. מנוע התאמה בסיסי (Match)
6. הצעות מחיר (Quote)
7. עסקאות (Deal) ותשלום בסיסי
8. מסמכים — ניהול קבצים וגרסאות בסיסי (ללא חתימה דיגיטלית אמיתית עדיין)
9. דוחות ליבה
10. יומן ביקורת (Audit Log) — חוצה את כל שאר המודולים

מודולים שנדחים בכוונה לשלב 2 ואילך (לפי סעיפים 22 ו-40 במסמך האפיון): אוטומציות, הודעות
אמיתיות ב-WhatsApp/SMS/Email, חתימה דיגיטלית, סליקת תשלומים אמיתית, הנהלת חשבונות,
פרסום ואינטגרציות חיצוניות, טרייד-אין מתקדם, פורטלי לקוח/ספק, BI מתקדם, יכולות AI.

## עקרונות שמונעים בעיות בעתיד
- לכל ישות מזהה פנימי קבוע, לא תלוי במספר רישוי/טלפון (הם יכולים להשתנות).
- לכל ישות: `id`, `created_at`/`created_by`, `updated_at`/`updated_by`, `deleted_at` (מחיקה לוגית).
- שדה `version` בישויות רגישות לעריכה מקבילה (Optimistic Locking) — מונע מצב שבו שני עובדים
  עורכים את אותה רשומה ודורסים אחד את השני (תרחיש קצה מפורש בסעיף 21 של מסמך האפיון).
- טבלת `AuditLog` גנרית: `entity_type`, `entity_id`, `actor_id`, `action`, `before`, `after`, `created_at`.
- חישובי מחיר ורווח מרוכזים בשירות אחד בלבד (לא משוכפלים בכמה מקומות), עם בדיקות יחידה.
