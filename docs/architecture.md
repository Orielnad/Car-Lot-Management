# ארכיטקטורה — מערכת ניהול מגרש רכבים

## סטטוס
שלב 0 (תכנון). מסמך זה הוא מקור האמת לארכיטקטורה, ומתעדכן כשמתקבלות החלטות נוספות
בתהליך ה-Discovery (סעיף 25 במסמך האפיון). אין לבנות תכונה שסותרת אותו בלי לעדכן אותו קודם.

## עקרונות מנחים (מתוך מסמך האפיון, סעיפים 18 ו-39.3)
- Backend עם API מתועד (OpenAPI); כל פעולה רגישה נבדקת בצד השרת — הסתרת כפתור בממשק אינה הרשאה.
- מסד נתונים רלציוני עם עסקאות (Transactions) ונעילות ברמת שורה, למניעת מכירת רכב כפול ועדכונים סותרים.
- מחיקה לוגית בלבד (`deleted_at`); היסטוריה עסקית לא נמחקת; שינויים רגישים מתועדים ביומן ביקורת.
- הפרדת סביבות Dev / Test / Prod; Migrations מתועדים והפיכים (עם סקריפט Rollback).
- תמיכה מלאה ב-RTL ובעברית פשוטה בממשק (ראו `design-system.md`).
- אינטגרציות חיצוניות (יד2, WhatsApp, סליקה, הנה"ח וכו') ממומשות מאחורי מתאם (Adapter) ייעודי, כך שאפשר להחליף ספק בלי לשנות את הליבה.

## מחסנית טכנולוגית
| שכבה | טכנולוגיה | למה |
|---|---|---|
| Frontend | React + TypeScript | תמיכה טובה ב-RTL, קהילה גדולה, מתאים לטבלאות מסוג Excel ולטפסים מודרכים |
| Backend | Node.js + TypeScript (NestJS) | מבנה מודולרי שמתאים לבניה הדרגתית לפי המודולים במסמך האפיון; תמיכה מובנית ב-OpenAPI |
| מסד נתונים | PostgreSQL | רלציוני, תומך בעסקאות ונעילות כנדרש בכלל העסקי "לא ניתן למכור אותו רכב פעמיים" |
| ORM / Migrations | Prisma | Migrations מתועדים, קריאים והפיכים |
| תורים (Queue) | Redis + BullMQ | הודעות, אוטומציות, הפקת מסמכים — נדרש משלב 2 ואילך, אך התשתית תוכן מוקדם |
| אחסון קבצים | אחסון תואם S3, מוצפן | קישורים זמניים להורדה, הגבלת סוג/גודל קובץ, ללא גישה ישירה |
| אימות | JWT + RBAC בצד שרת | MFA (TOTP) יתווסף כאופציה בהמשך |
| אירוח | ייקבע בפועל לפי תקציב (למשל Railway/Render להתחלה) | לא חוסם את הפיתוח; ניתן לשנות ללא שינוי בקוד האפליקציה |

## היקף (Scope) לשלב זה
מגרש רכבים יחיד, עם אפשרות למספר סניפים תחת אותו עסק (כנדרש כבר בסעיף 2 של מסמך האפיון).
המודל נבנה כך שלא יחסום הרחבה עתידית ל-Multi-tenant אמיתי (מספר עסקים נפרדים, שלב 4 בלבד),
אך שלב זה לא ייבנה כעת.

## מבנה מודולים (Epics) ל-MVP
1. משתמשים, הרשאות וסניפים (Auth / RBAC / Organization / Branch)
2. מלאי רכבים (Vehicle, סטטוסים, היסטוריה, עלויות בסיסיות)
3. CRM: לקוחות ולידים
4. משימות ויומן
5. מנוע התאמה בסיסי (Match)
6. הצעות מחיר (Quote)
7. עסקאות (Deal) ותשלום בסיסי
8. מסמכים — ניהול קבצים וגרסאות בסיסי (ללא חתימה דיגיטלית אמיתית עדיין)
9. דוחות ליבה
10. יומן ביקורת (Audit Log) — חוצה את כל שאר המודולים

מודולים שנדחים בכוונה לשלב 2 ואילך (לפי סעיפים 22 ו-40 במסמך האפיון): אוטומציות, הודעות
אמיתיות ב-WhatsApp/SMS/Email, חתימה דיגיטלית, סליקת תשלומים אמיתית, הנהלת חשבונות,
פרסום ואינטגרציות חיצוניות, טרייד-אין מתקדם, פורטלי לקוח/ספק, BI מתקדם, יכולות AI.

## עקרונות שמונעים בעיות בעתיד
- לכל ישות מזהה פנימי קבוע, לא תלוי במספר רישוי/טלפון (הם יכולים להשתנות).
- לכל ישות: `id`, `created_at`/`created_by`, `updated_at`/`updated_by`, `deleted_at` (מחיקה לוגית).
- שדה `version` בישויות רגישות לעריכה מקבילה (Optimistic Locking) — מונע מצב שבו שני עובדים
  עורכים את אותה רשומה ודורסים אחד את השני (תרחיש קצה מפורש בסעיף 21 של מסמך האפיון).
- טבלת `AuditLog` גנרית: `entity_type`, `entity_id`, `actor_id`, `action`, `before`, `after`, `created_at`.
- חישובי מחיר ורווח מרוכזים בשירות אחד בלבד (לא משוכפלים בכמה מקומות), עם בדיקות יחידה.

## סטטוס מודולים
| מודול | סטטוס |
|---|---|
| 1. משתמשים, הרשאות וסניפים | ✅ בוצע — Auth (JWT), RBAC בצד שרת, יומן ביקורת, Optimistic Locking על משתמשים |
| 2. מלאי רכבים | ✅ בוצע — State Machine לסטטוסים, מניעת כפילות רישוי/VIN, Optimistic Locking, הסתרת שדות עלות לפי הרשאה, היסטוריית אירועים (VehicleEvent), עלויות (Expense) |
| 3. CRM: לקוחות ולידים | ✅ בוצע — מניעת כפילות לקוח לפי טלפון, הרשאה ברמת שורה (איש מכירות רואה/עורך רק לידים שהוקצו לו), סטטוס ליד גמיש עם אכיפת "הפסד דורש סיבה" ונעילת לידים סגורים |
| 4. משימות ויומן | ✅ בוצע — משימות אישיות (`/tasks/mine`) עם הרשאה ברמת שורה כמו לידים, קישור פולימורפי לליד/לקוח/רכב/עסקה, נעילת משימה סגורה |
| 5. מנוע התאמה בסיסי | ✅ בוצע — ציון 0-100 מוסבר (לא רק מספר), חישוב טהור וניתן לבדיקה (`match-score.ts`), הרצה על כל הרכבים הזמינים לפי ליד, כיוון הפוך (רכב→לידים) לבעלי תפקידי ניהול מלאי בלבד |
| 6. הצעות מחיר | ✅ בוצע — זרימת סטטוס לינארית (DRAFT→SENT→VIEWED→APPROVED/REJECTED/EXPIRED), גרסאות ללא דריסה (revise יוצר שורה חדשה עם supersedesId), מדרגת אישור להנחה מעל 10% (רק Owner/SalesManager) |
| 7. עסקאות ותשלום בסיסי | ✅ בוצע — Deal+Payment, מניעת מכירה כפולה של אותו רכב באמצעות Partial Unique Index **ברמת מסד הנתונים** (לא רק בקוד — נבדק גם ב-SQL ישיר), סנכרון סטטוס רכב אוטומטי (SOLD/DELIVERED/חזרה ל-AVAILABLE בביטול), חסימת מסירה ללא תשלום מלא |
| 8. מסמכים | ✅ בוצע — העלאה/הורדה של קבצים (PDF/JPG/PNG בלבד, עד 10MB), אחסון מקומי בפיתוח מאחורי מתאם ייעודי (יוחלף ב-S3 בייצור בלי לשנות את שאר הקוד), שם קובץ אקראי בדיסק (לא שם המשתמש — מונע Path Traversal), גרסאות ללא דריסה כמו הצעות מחיר, הרשאה בירושה מהישות המקושרת (ליד/עסקה) |
| 9. דוחות ליבה | ✅ בוצע — דוח מלאי (מונים לפי סטטוס, שווי מלאי זמין, גיל ממוצע), דוח מכירות (הכנסה, מחיר ממוצע), דוח לידים (משפך המרה), "הביצועים שלי" לכל עובד — כל הנוסחאות בקובץ טהור ונבדק (`report-math.ts`), הרשאות לפי `docs/permissions.md` בדיוק |
| 10. יומן ביקורת | ✅ בוצע — נבנה כתשתית כבר במודול 1 (`AuditLogService`) ומאז נבדק שכל מודול עסקי חדש כותב אליו; נבדק כיסוי סופי: **20 נקודות רישום** פרושות על פני כל 9 המודולים העסקיים (משתמשים, סניפים, רכבים, לקוחות, לידים, משימות, הצעות, עסקאות, מסמכים) — כל פעולה רגישה (יצירה/שינוי סטטוס/תשלום) מתועדת |

**כל 10 מודולי ה-MVP הושלמו.** ראו `README.md` להרצה מקומית ו-`CONTRIBUTING.md` לתהליך העבודה. השלב הבא (לא MVP): Frontend, ואז שלב 2 לפי סדר העדיפויות בסעיף 40 של מסמך האפיון.

**הערה ידועה (Follow-up):** הודעות שגיאת ולידציה (DTO) עדיין באנגלית ברירת המחדל של class-validator ולא בעברית — לא נדרש תיקון כרגע כי אין עדיין Frontend שמציג אותן למשתמש, אבל יש לטפל בזה (למשל Validation Pipe מותאם עם הודעות בעברית) לפני שמתחילים לבנות ממשק.

## החלטות ותלויות שכדאי לדעת עליהן
- **NestJS 11 (לא 12):** גרסה 12 עברה ל-ESM בלבד (`"type": "module"`), מה שיוצר חיכוך
  משמעותי עם Jest/ts-node בפרויקט CommonJS רגיל. נבחרה 11.x (עדיין נתמכת ופעילה) לטובת
  יציבות ופשטות תחזוקה לצוות קטן.
- **Prisma 6 (לא 7):** גרסה 7 שינתה את אופן הגדרת חיבור מסד הנתונים (מעבר מ-`schema.prisma`
  ל-`prisma.config.ts` + Driver Adapters) — שינוי גדול מדי לתועלת נמוכה בשלב זה.
- **multer מקובע (`overrides`) לגרסה 7.10+ בטוחה:** `@nestjs/platform-express` מגרר כברירת
  מחדל גרסת multer עם חולשות DoS ידועות; ב-`backend/package.json` יש `overrides.multer`
  שמכריח גרסה מתוקנת.
- **חולשה ידועה ומתועדת (לא מתוקנת):** `prisma` (כלי ה-CLI, לא `@prisma/client` שרץ
  בפועל בשרת) תלוי ב-`deepmerge-ts` עם חולשת Stack Exhaustion. זהו כלי פיתוח בלבד
  (Migrations מקומיות/CI), לא חלק מהשרת הרץ בייצור, והסיכון בפועל נמוך. יש לעקוב אחרי
  עדכון של Prisma שיתקן זאת ולשדרג כשיהיה זמין.
- **פער ידוע בהעלאת קבצים (מודול 8):** נבדקים סוג קובץ (רשימה סגורה: PDF/JPG/PNG),
  גודל מקסימלי (10MB) והתאמה בין סיומת לסוג המוצהר. **לא מומש עדיין סריקת נוזקות**
  (Antivirus/מנוע סריקה) כנדרש בסעיף 17 במסמך האפיון — יש להוסיף זאת לפני שהמערכת
  מקבלת קבצים ממקורות שאינם עובדים מהימנים (למשל פורטל לקוח בעתיד).
